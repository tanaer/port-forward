# 回滚任务队列持久化限制声明

**⚠️ 重要：本文档明确说明回滚任务队列的设计限制**

## 当前实现

回滚任务队列在 Phase 2.3 中采用**内存中缓存**的设计：

### 存储位置
```go
// control/server/grpc_server.go:75-76
type NodeRegistry struct {
    nodes        map[string]*NodeInfo
    rollbackTasks map[string][]*RollbackTask  // 仅在内存中
    mu           sync.RWMutex
}
```

### 任务生命周期
1. **创建**：`PushRollbackToNode()` 将任务添加到内存队列
2. **处理**：`StreamConfig("get")` 时检查队列并发送任务给 Agent
3. **失败**：失败时自动重新入队（同一进程内）
4. **成功**：任务从队列移除

## ⚠️ 已知限制

### 1. 控制端重启时任务丢失
- **问题**：控制端进程重启后，内存中的所有待执行任务会丢失
- **影响**：未被 Agent 执行的回滚任务无法恢复
- **适用场景**：该设计适合快速操作，不适合长期待执行任务

### 2. 任务 ID 重复
```go
// control/server/grpc_server.go:1041
task.ID = int32(len(s.nodeRegistry.rollbackTasks[nodeID]) + 1)
```
- **问题**：任务 ID 基于队列长度生成，重启后从 1 重新计数
- **影响**：无法通过 TaskID 作为全局唯一标识追踪历史任务

### 3. 任务失败重试仅在内存中
- **当前机制**：失败任务自动重新入队（`EventRollbackTaskFailed` 事件）
- **限制**：
  - 仅在控制端进程运行期间有效
  - 进程崩溃时重试机制中断
  - 无持久化日志可供事后审计

## 生产使用建议

### ✅ 适合场景
- 实时配置回滚操作（立即执行）
- Agent 在线且可靠的网络环境
- 控制端可用性有保障（支持容错重启）

### ❌ 不适合场景
- 需要长期排队执行的回滚任务
- 对任务可靠性有高要求的环境
- 需要完整审计日志的合规场景

## 未来改进方向

### Phase 3 计划
为了达到生产级别的可靠性，建议：

1. **任务持久化**
   - 使用数据库存储待执行任务
   - 支持进程重启后恢复
   
2. **可靠的任务 ID**
   - 使用数据库生成的唯一 ID
   - 支持全局追踪

3. **完整的重试机制**
   - 可配置的重试策略（次数、间隔）
   - 死信队列机制
   - 完整的执行日志

4. **监控和告警**
   - 失败任务数量监控
   - EventRollbackTaskFailed 告警
   - 任务执行时间统计

## 当前补偿机制

虽然无持久化，但通过以下机制保证一定的可靠性：

1. **失败自动重试**
   - 失败任务立即重新入队
   - Agent 下次 get 请求时自动重试
   - 参考：`EventRollbackTaskFailed` 事件

2. **详细的错误日志**
   - 所有 JSON 解析错误都被记录
   - 失败原因明确输出给运维人员
   - 支持人工补投

3. **事件通知系统**
   - `EventRollbackTaskFailed` 发送给 WebSocket 客户端
   - 运维可实时看到失败状态
   - 支持配置告警
